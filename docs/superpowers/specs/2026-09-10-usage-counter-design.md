# ตัวนับการใช้งานเครื่องมือ — ดีไซน์

วันที่: 10 กันยายน 2569

## เป้าหมาย

เก็บจำนวนครั้งที่เครื่องมือแต่ละตัวถูกใช้จริง เพื่อ

1. แสดงให้ผู้ใช้เห็นว่าเครื่องมือนี้มีคนใช้ไปแล้วกี่ครั้ง
2. ให้ผู้ใช้เรียงรายการเครื่องมือตามความนิยมจริงได้

[DESIGN.md](../../../DESIGN.md) เขียนกำกับไว้ว่า _"อย่าแสดงความนิยมโดยไม่มีหลักฐานการใช้งานจริง"_ และ
`featuredRank` ที่ใช้อยู่เป็นการจัดอันดับโดยบรรณาธิการ ไม่ใช่ข้อมูลการใช้งาน งานนี้คือการสร้างหลักฐาน
ชิ้นที่ขาดไป โดย **ไม่แตะหน้าแรก** — "เครื่องมือแนะนำ" ยังเป็น `featuredRank` เหมือนเดิม

## ขอบเขต

ในขอบเขต

- ตารางเก็บยอดใน D1 พร้อม migration
- `POST /api/usage` สำหรับบันทึก และ `GET /api/usage` สำหรับอ่านสรุป
- แสดงยอดบนการ์ดในหน้า `/tools` และ `/categories/<id>`
- แสดงยอดในหน้าเครื่องมือแต่ละตัว
- ตัวเลือกเรียง "ยอดนิยม" ในหน้า `/tools`

นอกขอบเขต

- หน้าแรก (`/`) ไม่เปลี่ยน
- ไม่มีหน้าแดชบอร์ดสถิติสำหรับทีม
- ไม่มี rate limit เชิงลึกหรือระบบตรวจจับบอท
- ไม่แตะ vertical (หวย ทำนายฝัน ดูดวง) เพราะไม่ใช่ "เครื่องมือ" ใน registry

## การตัดสินใจที่ยืนยันแล้ว

| ประเด็น            | ข้อสรุป                                                                           |
| ------------------ | --------------------------------------------------------------------------------- |
| นิยามการนับ        | นับสองชั้นแยกกัน — `view` (เปิดหน้า) และ `use` (ลงมือใช้จริง)                      |
| ตัวเลขที่แสดง      | ยอด `use` สะสมทั้งหมด                                                             |
| ตัวเลขที่จัดอันดับ | ยอด `use` ใน 30 วันล่าสุด                                                         |
| ความสด             | หน่วงได้ ~10 นาที ผ่าน edge cache                                                 |
| ยอดยังน้อย         | ซ่อนตัวเลขจนกว่าจะถึงเกณฑ์ ไม่แสดงเลขหลักเดียว                                    |
| ที่เก็บ            | D1 ถังรายวัน ไม่ใช่ Analytics Engine และไม่ใช่ Durable Object                      |
| จุดยิงเหตุการณ์    | `ToolIsland` จุดเดียว ไม่แตะ `Tool.tsx` ทั้ง 45 ไฟล์                              |

## สถาปัตยกรรม

```
เบราว์เซอร์
  │  ToolIsland mount        → sendBeacon POST /api/usage {slug, kind:"view"}
  │  ผู้ใช้ลงมือใช้ครั้งแรก  → sendBeacon POST /api/usage {slug, kind:"use"}
  ↓
Astro API route (prerender=false) → src/lib/usage-worker.ts → D1 usage_daily
  ↑
  │  GET /api/usage  (Cache-Control s-maxage=600)
  │
เบราว์เซอร์ ← สรุปยอดต่อ slug → การ์ด, หน้าเครื่องมือ, ตัวเลือกเรียง
```

หน้าอื่นทั้งหมดยังเป็น static ที่เสิร์ฟจาก edge เหมือนเดิม สถาปัตยกรรม static-first ไม่เปลี่ยน —
`/api/usage` เป็นเส้นทาง dynamic เส้นที่สองของเว็บ ต่อจาก `/api/lottery/latest`

## 1. โครงข้อมูล

ฐานข้อมูล D1 ชื่อ `toolsiam-usage` binding ชื่อ `USAGE`

```sql
-- migrations/0001_usage_daily.sql
CREATE TABLE IF NOT EXISTS usage_daily (
  slug  TEXT    NOT NULL,
  day   TEXT    NOT NULL,
  views INTEGER NOT NULL DEFAULT 0,
  uses  INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY (slug, day)
) WITHOUT ROWID;

CREATE INDEX IF NOT EXISTS usage_daily_day ON usage_daily (day);
```

`day` เป็น `YYYY-MM-DD` ตามเวลา **Asia/Bangkok** ไม่ใช่ UTC ของ Worker คำนวณด้วย `todayInBangkok()`
ที่มีอยู่แล้วใน `src/lib/today.ts` มิฉะนั้นเส้นแบ่งวันจะขยับ 7 ชั่วโมงและยอด "30 วันล่าสุด" จะคลาดเคลื่อน

หนึ่งแถวคือสรุปของหนึ่งเครื่องมือในหนึ่งวัน **ไม่มี IP ไม่มี user agent ไม่มีคุกกี้ ไม่มีตัวระบุผู้ใช้**
สอดคล้องกับหลักการที่ [wrangler.jsonc](../../../wrangler.jsonc) เขียนกำกับไว้แล้วว่าเว็บนี้ไม่เก็บข้อมูลผู้ใช้

ขนาดตาราง: 45 เครื่องมือ × 365 วัน ≈ 16,000 แถวต่อปี ไม่ต้องมีงานลบข้อมูลเก่าในเฟสนี้

## 2. ทางเขียน — `POST /api/usage`

ไฟล์ `src/pages/api/usage.ts` ไฟล์เดียว export ทั้ง `POST` (บันทึก) และ `GET` (อ่านสรุป) ตั้ง
`export const prerender = false` และโยน logic ทั้งหมดไปที่
`src/lib/usage-worker.ts` ตามแบบเดียวกับ `src/lib/lottery-worker.ts` เพื่อให้ทดสอบได้โดยไม่ต้องมี runtime จริง

Request body:

```json
{ "slug": "thai-income-tax", "kind": "view" }
```

ส่งด้วย `navigator.sendBeacon` เพื่อไม่ให้เหตุการณ์หายเมื่อผู้ใช้ปิดแท็บทันที `sendBeacon` ส่ง
`Content-Type: text/plain` จึงต้องอ่าน body เป็น text แล้ว `JSON.parse` เอง ไม่ใช้ `request.json()`
ถ้าเบราว์เซอร์ไม่มี `sendBeacon` ให้ถอยไปใช้ `fetch(..., { keepalive: true })`

ด่านตรวจก่อนแตะ D1 เรียงตามลำดับ:

1. `env.USAGE_COUNTER !== 'on'` → 204 — kill switch แบบเดียวกับ `LOTTERY_AUTO` ปิดได้จาก dashboard โดยไม่ต้อง deploy
2. ไม่มี `env.USAGE` binding → 204 เงียบ ๆ (dev ที่ไม่ได้ผูก D1 ต้องไม่พัง)
3. `Origin` ไม่ตรงโดเมนของเรา (`https://toolsiam.com`, `https://www.toolsiam.com` หรือ `http://localhost:<port>` ใด ๆ สำหรับ dev) → 403
4. body ยาวเกิน 200 ไบต์ หรือ parse ไม่ผ่าน หรือ `kind` ไม่ใช่ `view`/`use` → 400
5. `slug` ไม่อยู่ใน allowlist ที่ generate จาก registry ตอน build → 400

allowlist สำคัญเพราะไม่มีมันใครก็ยิง slug สุ่มเข้ามาทำให้ตารางบวมได้ไม่จำกัด

การเขียน:

```sql
INSERT INTO usage_daily (slug, day, views, uses) VALUES (?1, ?2, ?3, ?4)
ON CONFLICT (slug, day) DO UPDATE SET views = views + ?3, uses = uses + ?4
```

ตอบ `204 No Content` เสมอเมื่อผ่าน ไม่คืนข้อมูลใดกลับไป

### การกันนับซ้ำ

อยู่ที่ฝั่งเบราว์เซอร์ด้วย `sessionStorage` คีย์ `toolsiam-usage:<slug>` เก็บว่า `view` และ `use`
ยิงไปแล้วหรือยัง หนึ่งเครื่องมือจึงนับได้อย่างละหนึ่งครั้งต่อหนึ่งเซสชัน ปิดแท็บแล้วกลับมาใหม่
ถือเป็นการใช้งานครั้งใหม่จริง ๆ ซึ่งตรงกับสัญชาตญาณของคำว่า "ใช้ไปกี่ครั้ง"

`sessionStorage` อาจโยน exception ในโหมดที่เบราว์เซอร์ปิดที่เก็บข้อมูล ทุกจุดที่อ่าน/เขียนต้องอยู่ใน
`try/catch` และเมื่อล้มเหลวให้ถือว่ายังไม่เคยยิง

**ข้อจำกัดที่ต้องยอมรับและต้องบอกผู้ใช้:** การกันซ้ำอยู่ฝั่งเบราว์เซอร์จึงปลอมได้ ตัวเลขนี้เป็น
ตัวชี้วัดโดยประมาณ ไม่ใช่ตัวเลขที่ตรวจสอบย้อนได้

### `use` เกิดขึ้นเมื่อไร

`ToolIsland` ผูก listener `input`, `change` และ `click` แบบ capture ไว้ที่กล่องครอบเครื่องมือ
เหตุการณ์แรกที่เกิดขึ้นในเซสชันนั้นคือ `use` แล้วถอด listener ทิ้ง

นิยามนี้คือ "มีคนเข้ามาลงมือใช้จริง" ซึ่งรวมคนที่พิมพ์แล้วเลิกกลางคันด้วย ที่ไม่นับ "ได้ผลลัพธ์ที่ถูกต้อง"
เพราะเครื่องมือส่วนใหญ่คำนวณสดขณะพิมพ์ ไม่มีปุ่ม "คำนวณ" การนับทุกครั้งที่ผลลัพธ์เปลี่ยนจะพองตาม
จำนวนตัวอักษรที่พิมพ์ และนิยาม "ผลลัพธ์ที่ใช้ได้" ต่างกันทุกเครื่องมือ

โครงข้อมูลรองรับการยกระดับภายหลัง: ถ้าอยากให้เครื่องมือตัวใดรายงานเองเมื่อได้ผลลัพธ์จริง
ทำได้ทีละตัวโดยไม่ต้องย้ายข้อมูลหรือเปลี่ยนสคีมา

## 3. ทางอ่าน — `GET /api/usage`

Query เดียวได้ทั้งยอดสะสมและยอด 30 วัน:

```sql
SELECT slug,
       SUM(uses) AS total,
       SUM(CASE WHEN day >= ?1 THEN uses ELSE 0 END) AS recent
FROM usage_daily
GROUP BY slug
```

`?1` คือวันที่ของ 29 วันก่อนหน้าวันนี้ตามเวลา Asia/Bangkok (รวมวันนี้เป็น 30 วัน)

Response:

```json
{
  "generatedAt": "2026-09-10T14:05:00.000Z",
  "tools": { "thai-income-tax": { "total": 1234, "recent": 210 } }
}
```

Headers: `Cache-Control: public, max-age=60, s-maxage=600, stale-while-revalidate=3600`

edge cache ทำให้ตัวเลขหน่วงไม่เกิน ~10 นาทีตามที่ตกลง และ D1 ถูก query จริงราว 144 ครั้งต่อวัน
ไม่ว่าจะมีผู้เข้าชมกี่คน

ถ้า binding หายหรือ kill switch ปิด → `204` → ฝั่งเว็บไม่แสดงตัวเลขและเรียงตามลำดับเดิม
แบบเดียวกับที่ `LiveDrawNotice` ถอยกลับไปใช้ข้อมูล static เมื่อ API หวยมีปัญหา

## 4. ฝั่งแสดงผล

### `src/lib/usage.ts` — ฟังก์ชันบริสุทธิ์

- `type UsageSummary = { generatedAt: string; tools: Record<string, { total: number; recent: number }> }`
- `USE_DISPLAY_THRESHOLD = 50` — ต่ำกว่านี้ไม่แสดงตัวเลข
- `POPULAR_SORT_MIN_TOOLS = 5` — ต้องมีเครื่องมือผ่านเกณฑ์อย่างน้อยเท่านี้ ตัวเลือกเรียง "ยอดนิยม" จึงจะปรากฏ
- `formatUseCount(n)` → `"ใช้ไปแล้ว 1,234 ครั้ง"` ใช้ `formatNumber()` จาก `src/lib/format.ts` เพื่อให้ตัวคั่นหลักพันเป็นชุดเดียวกับทั้งเว็บ
- `sortByPopularity(tools, summary)` — เรียงด้วย `recent` มากไปน้อย เสมอกันใช้ `total` เสมอกันอีก
  ใช้ลำดับใน registry เป็นตัวตัดสิน เพื่อให้ผลเรียงนิ่ง ไม่สลับตำแหน่งไปมาระหว่างการ render

### `src/lib/usage-client.ts` — ฝั่งเบราว์เซอร์

- `recordUsage(slug, kind)` — กันซ้ำด้วย sessionStorage แล้วยิง beacon ล้มเหลวเงียบเสมอ
- `fetchUsageSummary()` — เก็บ promise ไว้ที่ระดับโมดูล ทุกไอส์แลนด์ในหน้าเดียวกันจึงยิงจริงครั้งเดียว
  ล้มเหลวหรือได้ 204 → คืน `null`

### หน้า `/tools`

`ToolSearch.tsx` ต้องถือข้อมูลสรุปอยู่แล้วเพื่อเรียงลำดับ จึงส่งตัวเลขลงเป็น prop `useCount` ให้
`ToolCard.tsx` ตรง ๆ ตามแนวทาง React ปกติ

ตัวเลือกเรียงใช้ `SegmentedControl` ที่มีอยู่แล้ว วางถัดจากแถว CategoryPill:

- `ตามหมวด` (ค่าเริ่มต้น ลำดับตาม registry เหมือนวันนี้)
- `ยอดนิยม`

จำสถานะใน URL เป็น `?sort=popular` แบบเดียวกับ `q` และ `category` ที่ทำอยู่ และการเปลี่ยนค่าเรียง
สร้าง history entry เหมือนการเปลี่ยนหมวด

ตัวเลือก `ยอดนิยม` **ไม่ปรากฏ** จนกว่าจะมีเครื่องมือผ่านเกณฑ์ครบ `POPULAR_SORT_MIN_TOOLS` ตัว
ถ้า URL มี `?sort=popular` มาแต่ยังไม่ถึงเงื่อนไข ให้ถอยไปใช้ `ตามหมวด` เงียบ ๆ

### หน้าหมวดและหน้าเครื่องมือ

สองหน้านี้เป็น HTML ล้วนไม่มีไอส์แลนด์ที่ถือ state ของการ์ด จึงใช้สคริปต์เล็ก ๆ
`src/scripts/usage-counts.ts` เติมตัวเลขลงช่อง `[data-usage-slug]` โดยเรียก `fetchUsageSummary()`
ก้อนเดียวกับฝั่ง React

`ToolCard.tsx` จะ render ช่องว่างนี้เสมอ และตั้ง `data-usage-managed` เมื่อถูก React คุมค่าอยู่แล้ว
เพื่อให้สคริปต์ข้ามการ์ดในหน้า `/tools` ไป ทั้งสองทางจึงไม่มีวันเขียนทับกัน

ข้อความในหน้าเครื่องมือยาวกว่าบนการ์ด: `มีคนใช้เครื่องมือนี้แล้ว 1,234 ครั้ง` พร้อมหมายเหตุกำกับว่า
นับหนึ่งครั้งต่อการเข้าใช้หนึ่งครั้ง เริ่มนับตั้งแต่วันที่เปิดใช้ระบบ และเป็นตัวเลขโดยประมาณ

### สิ่งที่จะไม่ทำ

ตัวเลขไม่อยู่ใน HTML ที่ crawler เห็น (มาหลัง hydration เสมอ) และไม่เข้า structured data ใด ๆ
มันเป็นข้อมูลประกอบการตัดสินใจของคน ไม่ใช่สัญญาณ SEO และไม่มีทางกลายเป็นตัวเลขที่ Google อ้างอิง

ช่องแสดงตัวเลขต้องจองพื้นที่ไว้ล่วงหน้าหรือไม่กินพื้นที่เลยเมื่อว่าง เพื่อไม่ให้เกิด layout shift
ตอนตัวเลขมาถึง

## 5. ช่วงเริ่มต้น

ทุกเครื่องมือเริ่มที่ 0 และไม่มีข้อมูลย้อนหลังให้กู้คืน ช่วงแรกจึงจะไม่มีตัวเลขปรากฏที่ใดเลย
และไม่มีตัวเลือกเรียง "ยอดนิยม" ซึ่งเป็นพฤติกรรมที่ตั้งใจ ไม่ใช่ความผิดพลาด

เกณฑ์ทั้งสองค่าอยู่ในไฟล์เดียวกันและปรับได้ด้วยการแก้ค่าคงที่ตัวเดียว

## 6. การทดสอบ

| ชั้น       | ครอบอะไร                                                                                      |
| ---------- | --------------------------------------------------------------------------------------------- |
| `usage.ts` | รูปแบบตัวเลขไทย เกณฑ์ซ่อน/แสดง ความเสถียรของ comparator เมื่อยอดเท่ากัน                        |
| `usage-worker.ts` | kill switch ปิด, ไม่มี binding, Origin ผิด, body พัง/ยาวเกิน, `kind` ผิด, slug นอก allowlist, พารามิเตอร์ SQL ของทั้งเขียนและอ่าน ด้วย D1 stub |
| `usage-client.ts` | กันซ้ำต่อเซสชัน, sessionStorage โยน exception แล้วยังทำงานต่อได้, ล้มเหลวเงียบ            |
| คอมโพเนนต์ | การ์ดแสดง/ไม่แสดงตัวเลขตามเกณฑ์, ToolSearch เรียงยอดนิยมถูกต้อง, `?sort=popular` restore/persist, ตัวเลือกซ่อนเมื่อข้อมูลยังน้อย |

ไม่มีเทสต์ใดยิงเน็ตจริง จากนั้น verify ของจริงด้วย `wrangler dev` กับ D1 local แล้วเปิดในเบราว์เซอร์
ตรวจว่ายิง POST จริง ตัวเลขขึ้น และเรียงลำดับได้

## 7. ความเสี่ยงและข้อจำกัด

- **เพดาน D1 free tier** — เขียนหนึ่งแถวต่อหนึ่งเหตุการณ์ Free tier หยุดทำงานทันทีที่เกิน 100,000 rows write
  ต่อวัน (ดู [spec เดิม](2026-09-07-toolsiam-design.md)) ทราฟฟิกปัจจุบันห่างเพดานมาก แต่ถ้าโตจนชน
  ต้องย้ายไป Analytics Engine — ถังรายวันชุดนี้ย้ายได้โดยไม่เสียข้อมูลเก่า
- **ยอดปลอมได้** — ใครก็ยิง `POST /api/usage` ตรงได้ กันไว้แค่ Origin, allowlist และ kill switch
  เฟสนี้ไม่ทำ rate limit เชิงลึกโดยตั้งใจ เพราะเดิมพันต่ำ (ไม่มีเงิน ไม่มีบัญชี ไม่มีอันดับที่ใครได้ประโยชน์)
- **`use` นับกว้างกว่าความจริง** — คนที่พิมพ์แล้วเลิกกลางคันถูกนับด้วย ยกระดับทีละเครื่องมือได้ภายหลัง
- **ไม่มีข้อมูลย้อนหลัง** — เริ่มนับจากศูนย์ในวันที่ deploy

## 8. งานที่ต้องทำนอกโค้ด

1. `wrangler d1 create toolsiam-usage` แล้วนำ `database_id` ใส่ `wrangler.jsonc`
2. รัน migration ทั้ง local และ production
3. ตั้ง var `USAGE_COUNTER` เป็น `"on"` ใน `wrangler.jsonc`
