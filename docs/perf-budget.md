# Performance Budget

ตัวเลขในไฟล์นี้ **วัดจากของจริง ไม่ได้ตั้งเอาไว้ล่วงหน้า** (§21.2) — เดาตัวเลขแล้วจะได้ gate ที่หลวมจนไร้ประโยชน์
หรือแน่นจนบล็อกงานโดยไม่มีเหตุผล

```bash
npm run size          # วัดแล้วเทียบกับ budget ด้านล่าง — เกิน = exit 1
npm run size -- --json  # ผลดิบ ใช้ตอนตั้ง baseline ใหม่
```

`npm run size` นับ "JS ของหน้า" เป็นไฟล์ที่เบราว์เซอร์ต้องโหลดจริงจนหน้าทำงานครบ: script ที่อ้างจาก HTML
บวก static import ที่ตามไปจนสุด บวก chunk ของเครื่องมือที่ `ToolIsland` โหลดแบบ dynamic
(อ่านจากตาราง `__vite__mapDeps` ที่ Vite ใส่ไว้ จึงตรงกับสิ่งที่โหลดจริง ไม่ใช่การประมาณ)

## Budget ปัจจุบัน

`budget = baseline_p95 × 1.15` (tolerance +15%) · หน่วยเป็น byte หลัง gzip

```json
{
  "measuredAt": "2026-09-08",
  "basis": "baseline_p95 × 1.15 (Phase 1)",
  "limits": {
    "cssGzip": 8597,
    "toolPageJsP95": 120591,
    "toolPageHtmlP95": 10524,
    "contentPageJsP95": 104975,
    "contentPageHtmlP95": 12411
  }
}
```

`npm run size` ตรวจสองชั้น: ค่า p95 ของแต่ละกลุ่ม และ **หน้ารายหน้า** — หน้าเดียวที่โดดขึ้นมาเกิน budget
ของกลุ่มตัวเองก็ fail แม้ p95 จะยังผ่าน

## กติกาการแก้ budget

1. **เกิน budget = fail** — แก้ให้เล็กลงก่อนเป็นทางเลือกแรกเสมอ
2. **ยกระดับ budget ได้** ถ้าการเพิ่มขึ้นมีเหตุผลที่อธิบายได้ โดยต้องบันทึกลงตารางด้านล่าง
   พร้อมชื่อ Phase เหตุผล และตัวเลขใหม่ — ห้ามแก้ตัวเลขเงียบ ๆ
3. **ทบทวน baseline ทุกครั้งที่จบ Phase** — วัดใหม่ ตั้ง budget ใหม่จาก baseline ที่วัดได้
4. ห้ามเพิ่ม production dependency หรือ devDependency เพื่อแก้ปัญหาขนาด (PF2 / E8)
